# 設定

Queruneの環境変数、ログイン方式、多要素認証、Search ConsoleとGA4の接続をまとめます。

## 環境変数

環境変数は、Cloudflareのダッシュボード（Workersの「Settings」→「Variables and Secrets」）か`wrangler secret put`で設定します。`wrangler.jsonc`には書きません。再デプロイで設定が上書きされないようにするためです。

| 名前 | 必須 | 内容 |
| --- | --- | --- |
| `JWT_SECRET` | 必須 | ログインのセッションに使う秘密の値。32文字以上。`openssl rand -hex 32`で生成します。変更すると全員がログアウトします |
| `AUTH_MODE` | 任意 | ログイン方式。`password`（既定）か`oidc` |
| `APP_ORIGIN` | `oidc`で必須 | QueruneのURLのオリジン（例：`https://querune.example.com`）。`password`では、設定するとパスキーで多要素認証できます |
| `OIDC_ISSUER` | `oidc`で必須 | IdPのissuer |
| `OIDC_CLIENT_ID` | `oidc`で必須 | IdPに登録したクライアントのID |
| `OIDC_CLIENT_SECRET` | `oidc`で必須 | IdPに登録したクライアントのシークレット |
| `INITIAL_ADMIN_EMAIL` | `oidc`で最初の1人に必須 | 最初のadminのメールアドレス。ユーザーが0人のときだけ、このメールアドレスでログインした人をadminにします。下記を参照 |
| `OIDC_REQUIRE_EMAIL_VERIFIED` | 任意 | `false`にすると、IdPが`email_verified`を送らない場合もログインを許可します。下記を参照 |
| `OIDC_REQUIRE_GOOGLE_HD` | 任意 | `true`にすると、初めてのログインでGoogleの`hd`を確かめます。Gmailは対象外です。IdPのログイン方法がGoogleだけの場合に使います。下記を参照 |
| `PASSWORD_MFA_POLICY` | 任意 | 多要素認証を必須にする範囲。`optional`（既定）・`admins`・`all`のどれか（`AUTH_MODE=password`）。下記を参照 |
| `PASSWORD_MFA_KEY` | 任意 | 認証アプリ（TOTP）の秘密を暗号化する鍵。設定すると認証アプリで多要素認証できます（`AUTH_MODE=password`）。下記を参照 |
| `SESSION_MAX_AGE_HOURS` | 任意 | ログインからセッションが切れるまでの時間。既定は`password`で`720`（30日）、`oidc`で`24`です。下記を参照 |
| `SESSION_IDLE_TIMEOUT_HOURS` | 任意 | 最後のアクセスからセッションが切れるまでの時間。既定はなしです。下記を参照 |
| `GOOGLE_SERVICE_ACCOUNT_KEY` | 任意 | Search ConsoleとGA4の取り込みに必要。Googleのサービスアカウントの鍵（JSON）をそのまま設定します。下記を参照 |

## ログイン方式

### パスワード（`AUTH_MODE=password`）

既定のログイン方式です。デプロイしてURLを開くと初期設定画面になり、最初に登録した人がadminになります。初期設定はユーザーが1人もいない間は誰でも開けるので、デプロイしたらすぐに自分で済ませてください。

2人目以降は、adminが管理画面のユーザー管理で追加します。追加するときは、招待リンクを発行するか初期パスワードを決めます。

- 招待リンクは本人が開いて自分でパスワードを決めるためのURLです。発行から7日間有効で、1回だけ使えます。
- リンクは発行した直後に1回だけ表示されます。本人に渡してください。なくしたときや期限が切れたときは、ユーザー管理の「招待リンクを再発行」で新しいリンクを発行します。古いリンクは使えなくなります。
- パスワードを決めるまでは、一覧に「招待中」と表示されます。招待を取り消すときはユーザーを削除します。
- `APP_ORIGIN`を設定している場合、リンクはそのURLになります。設定していない場合は、管理画面を開いているURLになります。
- `PASSWORD_MFA_POLICY`で多要素認証が必須の人は、パスワードを決めた後に認証方法を登録します。

### OIDC（`AUTH_MODE=oidc`）

IdPのアカウントでログインします。ログインできるのは、adminが管理画面のユーザー管理で追加した人だけです。IdPでログインできることやドメインに所属していることだけでは、ユーザーは作られません。

- 最初のadminは`INITIAL_ADMIN_EMAIL`で決めます。ユーザーが1人もいないときだけ、このメールアドレスでログインした人がadminとして作られます。ユーザーが1人以上いれば、この設定は使われません。
- `INITIAL_ADMIN_EMAIL`を設定しないと、ユーザーがいない状態では誰もログインできません。形式が正しくないと、すべてのリクエストが500になります。
- 2人目以降は、adminがユーザー管理でメールアドレスとロールを指定して追加します。追加した人が初めてログインしたときに、IdPのアカウントと結び付きます。結び付いた後はIdPのアカウントで本人を確かめるので、IdP側でメールアドレスを変えてもログインできます。
- 追加してまだログインしていない人は、一覧に「招待中」と表示されます。
- ログインさせたくない人は削除します。削除するとセッションとMCPの接続も切れます。もう一度使えるようにするには、ユーザーを追加し直します。
- `OIDC_REQUIRE_EMAIL_VERIFIED=false`は、IdPが`email_verified`を送らず、かつIdPのすべてのログイン方法がメールアドレスを確認している場合にだけ設定してください。未確認のメールアドレスでログインできる方法があると、追加済みでまだログインしていない人や`INITIAL_ADMIN_EMAIL`になりすまして結び付けられるためです。`email_verified`が送られた場合は、この設定に関係なく`true`である必要があります。`OIDC_ISSUER`を変えたときは、この設定も見直してください。IdPが`email_verified`を送れるように設定できる場合は、そちらを優先します（Cloudflare Accessは下記を参照）。
- IdPには、リダイレクトURIとして`<APP_ORIGIN>/auth/oidc/callback`を登録します。

#### Cloudflare Access for SaaSでGoogleを使う場合

Cloudflare Access for SaaSは、Googleの`email_verified`と`hd`を既定ではIDトークンに入れません。AccessのアプリのOIDCクレームに、次の2つを追加します。

| 名前 | スコープ | IdPクレーム | 必須 |
| --- | --- | --- | --- |
| `email_verified` | `profile` | `verified_email` | オン |
| `hd` | `profile` | `hd` | オフ |

- それぞれ新しいクレームとして追加します。既存のクレームの下にある「IdPごとの値」は、そのクレームの値をIdPごとに上書きする設定です。そこに`hd`を入れると`email_verified`が`hd`の値になり、誰もログインできなくなります。
- `hd`は必須にしません。Gmailのアカウントには`hd`がないので、必須にするとAccessでログインに失敗します。
- `email_verified`を追加すれば、`OIDC_REQUIRE_EMAIL_VERIFIED`は既定（`true`が必要）のままで使えます。
- `hd`を追加したうえで、`OIDC_REQUIRE_GOOGLE_HD`を`true`にします（下記）。

#### Googleの`hd`の確認（`OIDC_REQUIRE_GOOGLE_HD`）

IdPのログイン方法がGoogleだけの場合（Cloudflare Access for SaaSでGoogleだけを選んだ場合など）に、`OIDC_REQUIRE_GOOGLE_HD`を`true`にします。Googleがメールアドレスの今の持ち主を保証できるのは、Gmailと、IDトークンに`hd`が入るGoogle Workspaceのアカウントだけです。会社のメールアドレスで作った個人のGoogleアカウントには`hd`がありません。

- 有効にすると、`@gmail.com`以外のメールアドレスでは、IDトークンの`hd`が空でない文字列のときだけログインを許可します。`hd`の値は確かめないので、協力先のWorkspaceのアカウントもログインできます。
- 確かめるのは、追加した人の初めてのログインと、`INITIAL_ADMIN_EMAIL`で最初のadminを作るときです。条件を満たさないと、ユーザーと結び付けず、「このアカウントではログインできません」と表示します。
- すでにIdPのアカウントと結び付いた人は確かめ直しません。有効にする前に結び付いた人もログインし続けられます。まだログインしていない人は、有効にした後の初めてのログインで確かめます。
- 有効にする前に、IdPがIDトークンに`hd`を入れるようにします。Cloudflare Accessでは、上記のとおりアプリのOIDCクレームに`hd`を追加します。`hd`が届かないと、Gmail以外の人は初めてのログインができません。拒否されたときは、ログに`oidc login rejected`（`reason: "google_hd_missing"`）が出ます。
- `INITIAL_ADMIN_EMAIL`が`hd`のないアカウント（Gmailでも、Workspaceでもないもの）だと、最初のadminを作れません。その場合は無効にしてadminを作ってから、有効にします。
- IdPは確かめません。Google以外のログイン方法があるIdPで有効にすると、Gmail以外の人がログインできないか、確認の意味がなくなります。
- 値は`true`か`false`（既定）です。それ以外の値では、初めてのログインと最初のadminの作成だけが500になり、ほかの機能は動き続けます。ログに`invalid configuration: OIDC_REQUIRE_GOOGLE_HD`が出ます。

#### `ALLOWED_EMAILS`を使っていた場合の更新

以前のQueruneは、`ALLOWED_EMAILS`に一致する人を初回ログインで自動的に作っていました。いまは`ALLOWED_EMAILS`を使わず、一覧にいる人は全員ログインできます。更新するときは次の手順に従ってください。

1. 更新する前に、管理画面のユーザー一覧を確認します。
2. ログインさせたくない人を削除します。対象は`ALLOWED_EMAILS`のドメイン指定や`*`で自動的に作られた人と、`ALLOWED_EMAILS`から外してログインを止めていた人です。削除するとセッションとMCPの接続も切れます。
3. 更新します。
4. `ALLOWED_EMAILS`の設定を消します。残っていても使われず、エラーにもなりません。

### 多要素認証（`AUTH_MODE=password`）

パスワードでログインする場合は、パスワードに加えてパスキー（セキュリティキーを含む）か認証アプリ（TOTP）で確認できます。OIDCの場合は、IdP側の多要素認証の設定に従います。

| 方式 | 使えるようにする設定 |
| --- | --- |
| パスキー・セキュリティキー | `APP_ORIGIN`にQueruneのURLのオリジンを設定します。`https://`で始まり、パスを含まない値にします。それ以外の値ではパスキーが使えません（エラーにはなりません） |
| 認証アプリ（TOTP） | `PASSWORD_MFA_KEY`に`openssl rand -base64 32`で生成した値をシークレットとして設定します |

- 何も設定しなければ多要素認証は使えず、これまでどおりパスワードだけでログインします。
- パスキーは`APP_ORIGIN`のホスト名に結び付きます。ドメインを変えると登録済みのパスキーは使えなくなります。
- `PASSWORD_MFA_KEY`を変えると登録済みの認証アプリが使えなくなります。その場合は復旧コードでログインして登録し直します。`JWT_SECRET`とは別に控えておいてください。

#### 登録と解除

ログイン画面の「多要素認証の設定」（`/auth/mfa/manage`）から登録します。メールアドレスとパスワードを入れてから、パスキーか認証アプリを登録します。

- 登録すると復旧コードが8個表示されます。表示されるのはこの1回だけです。認証端末とは別の場所に保存してください。各コードは1回だけ使えます。
- 認証方法の追加・入れ替え・解除には、パスワードと登録済みの認証方法（または復旧コード）が必要です。
- 端末をなくしたときは、ログインの確認画面の「復旧コードを使う」から復旧コードを入れます。認証方法を入れ替えることもできます。最後の1個を使うと、そのまま新しい認証方法の登録に進みます。
- adminがパスワードを再設定しても、そのユーザーの認証方法は残ります。
- adminはユーザー管理の「多要素認証をリセット」で、ほかのユーザーの多要素認証をリセットできます。認証方法と復旧コードがすべて削除され、そのユーザーのセッションとMCPの接続も切れます。パスワードは残ります。
- リセットした後は、パスワードだけで新しい認証方法を登録できます。本人であることを確かめてからリセットし、すぐにログインして登録してもらってください。端末と一緒にパスワードも漏れたおそれがあるときは、パスワードも再設定します。
- 自分自身の多要素認証はリセットできません。adminが1人だけでそのadminが認証方法と復旧コードをすべてなくしたときは、D1のMFAの行を直接削除します。手順は[workers-app-coreのREADME](https://github.com/i2bskn/workers-app-core#password-mfa)を参照してください。
- adminはパスワードと多要素認証の両方をリセットすれば、そのユーザーとしてログインできます。多要素認証はadminからユーザーを守るものではありません。

#### 必須にする範囲

`PASSWORD_MFA_POLICY`で、多要素認証を必須にする範囲を決めます。

| 値 | 動作 |
| --- | --- |
| `optional`（既定） | 必須にしません。登録したユーザーだけが、ログインのたびに確認します |
| `admins` | adminは登録しないとログインできません |
| `all` | 全員が登録しないとログインできません。初期設定で作る最初のadminも含みます |

- `admins`と`all`では、`APP_ORIGIN`か`PASSWORD_MFA_KEY`の少なくとも一方が必要です。どちらもないと、すべてのリクエストが500になります。
- パスキーだけを使う設定で`all`にした場合は、初期設定の画面を`APP_ORIGIN`のURLで開いてください。
- 設定はパスワードでログインし直したときに効きます。ログイン中のセッションとMCPの接続は切れません。セッションの更新でも確認は求められません。
- 確認の画面では、1回の確認につき5回まで入力できます。認証アプリのコードを何度も間違えると、そのユーザーの認証アプリでの確認にしばらく待ち時間がかかります。待っている間もパスキーと復旧コードは使えます。

### セッションの長さ

ログインのセッションの長さは`SESSION_MAX_AGE_HOURS`と`SESSION_IDLE_TIMEOUT_HOURS`で変えられます。どちらも時間単位の1〜9600の整数で、`"168"`のように文字列で設定します。それ以外の値を設定すると、すべてのリクエストが500になります。

- `SESSION_MAX_AGE_HOURS`はログインした時点から数えます。アクセスを続けても延長されません。変更は次のログインから反映されます。
- `SESSION_IDLE_TIMEOUT_HOURS`を設定すると、アクセスがないままその時間が経ったセッションも切れます。アクセスするたびに`SESSION_MAX_AGE_HOURS`の範囲で延長されます。変更は既存のセッションにもすぐ反映されます。
- 延長されるのは、アクセストークン（15分）が切れた後のアクセスです。そのため実際に許される無操作の時間は、`SESSION_IDLE_TIMEOUT_HOURS`より最大15分短くなります。
- MCPのトークンには影響しません。

たとえば「7日以内にアクセスすれば延長し、最長30日でログインし直す」なら、`SESSION_IDLE_TIMEOUT_HOURS`を`168`、`SESSION_MAX_AGE_HOURS`を`720`にします。

## ロール

| ロール | できること |
| --- | --- |
| admin | すべての操作と、ユーザー管理（追加・招待リンクの再発行・パスワードの再設定・多要素認証のリセット・セッションの失効・ロールの変更・削除） |
| member | ユーザー管理以外のすべての操作 |

全ユーザーが同じサイトの情報を見ます。サイトごと・ユーザーごとに見られる範囲を分ける機能はありません。最後のadminのロールは変更できず、削除もできません。自分自身は削除できません。

## Search Console と GA4 の接続

Queruneは、1つのGoogleのサービスアカウントで全サイトのSearch ConsoleとGA4のデータを読み取ります。

1. [Google Cloudのコンソール](https://console.cloud.google.com/)でプロジェクトを作ります（既存のプロジェクトでも構いません）。
2. 「APIとサービス」で、Google Search Console APIとGoogle Analytics Data APIを有効にします。
3. 「IAMと管理」→「サービスアカウント」でサービスアカウントを作り、「鍵」→「鍵を追加」→「新しい鍵を作成」でJSONの鍵を作ってダウンロードします。サービスアカウントにプロジェクトのロールは要りません。
4. 鍵のJSONを、`wrangler secret put GOOGLE_SERVICE_ACCOUNT_KEY`（JSONを貼り付けます）か、Cloudflareのダッシュボードの「Variables and Secrets」で、秘密（Secret）として`GOOGLE_SERVICE_ACCOUNT_KEY`に保存します。
5. Search Consoleで、プロパティの「設定」→「ユーザーと権限」にサービスアカウントのメールアドレス（鍵の`client_email`）を追加します。権限は「制限付き」で構いません。
6. GA4で、プロパティの「管理」→「プロパティのアクセス管理」にサービスアカウントのメールアドレスを「閲覧者」として追加します。
7. Queruneの管理画面でサイトにSearch ConsoleのプロパティとGA4のプロパティIDを設定し、サイトの画面の「データの取り込み」で期間を選んで取り込みます。

- 鍵はリポジトリや`.dev.vars.example`に置かないでください。鍵があれば、サービスアカウントに許可したすべてのプロパティのデータを読めます。
- サイトの画面の「データの取り込み」に、設定したサービスアカウントのメールアドレスが表示されます。鍵が未設定か読み取れない場合も、ここに表示されます。
- 鍵を作り直したときは、`GOOGLE_SERVICE_ACCOUNT_KEY`を新しい鍵に置き換えてから、Google Cloudで古い鍵を削除してください。
- 取り込みの仕組みと上限は[APIリファレンス](api.md#取り込みの仕組み)を参照してください。
